## 排障：本地启动后端的两个 404 / 503 报错

用户 uvicorn 启动 `app/main.py` 后遇到两个报错，均已定位：

1. `GET /` → 404 Not Found：**符合设计**。后端没有根路由 `@app.get("/")`，所有业务接口都在 `/api/` 前缀下（如 `/api/health`、`/api/sessions`）。FastAPI 自带 `/docs`（Swagger）可访问。真正的健康检查用 `GET /api/health`。

2. `/api/health` → 503 `DATABASE_UNAVAILABLE` + `OperationalError`：**根因是 `app/core/database.py` 用了相对路径 `sqlite:///./data/sqlite_demo.db`**，SQLite 相对路径按"启动时的 CWD"解析。IDE/直接 `python app/main.py` 常把 CWD 设成 `app/` 子目录，导致 `./data/...` 指向 `app/data/`（不存在）→ 打不开文件。已修复为基于项目根的绝对路径（`PROJECT_ROOT = Path(__file__).resolve().parents[2]`），实测从 `app/` 子目录也能连上。

结论：`data/sqlite_demo.db` 文件完好，无需重建；改路径即可。

## 排障：模型降级到 Mock（路由绑定错配，非网管问题）

用户用 DeepSeek（`DEEPSEEK_API_KEY` 真实可用），但 WS 聊天流出现 "模型路由 fast 不可用，降级到 Mock 结果"。
- 根因：`gateway.py` 的 `ROUTE_ENV["fast"]` 默认绑 **DashScope**（`MODEL_FAST=qwen-plus` + `DASHSCOPE_API_KEY`，而 .env 里该 Key 是占位符 `你的百炼key`）→ `_key_usable` 判不可用 → 降级。与网管/网络无关。
- 实测：`fast` available=False；`reasoning`（绑 `DEEPSEEK_API_KEY` + `MODEL_DS=deepseek-flash` 兜底）available=True。即 risk_extraction/reply/summary 节点其实在真调 ds，只有 intent/emotion/rewrite（用 `fast` 路由）降级。
- 已修复：把 `ROUTE_ENV["fast"]` 改为 `("MODEL_DS","DEEPSEEK_API_KEY","DEEPSEEK_BASE_URL")`，全链路统一走 DeepSeek。验证 `is_available("fast")=True` 且客户端可实例化 deepseek-flash。
- 注意：改代码后需**重启 uvicorn** 才生效。另：`main.py` WebSocket 端点仍硬编码 `"mode":"mock"`，即使配了真 Key，走 WS 聊天流也会强制 Mock；要真调模型需把那行改成 `"auto"`。

## 排障：模拟发消息后"一直卡着"（模型调用无超时）

用户反馈：模拟发消息后后端大模型分析卡死。排查：
- `config.MODEL_TIMEOUT_SECONDS`(=20) 与 `MODEL_MAX_RETRIES`(=1) **定义了却从未传入 ChatOpenAI 客户端**（`gateway.py` 的 `get()` 原只传 model/key/base_url/temperature）。导致模型调用走 SDK 默认超时（极长），一旦网络抖动/代理拦截就**无限挂起**，整条分析链路卡死。
- 已修复：在 `ChatOpenAI(...)` 中补 `timeout=float(os.getenv("MODEL_TIMEOUT_SECONDS","20"))`、`max_retries=int(os.getenv("MODEL_MAX_RETRIES","1"))`。
- 验证：沙箱用真实 `DEEPSEEK_API_KEY` 复现 `model=deepseek-flash` + `base_url=https://api.deepseek.com` 调用，1~2s 正常返回（模型名合法、接口可达）。说明"卡着"非模型/接口问题，而是缺超时。
- 提醒用户：沙箱能连通不代表其真机能连通（公司代理/防火墙/GFW 可能拦截 `api.deepseek.com`）。需**重启 uvicorn** 生效；若重启后仍走 Mock（≤20s 后降级），看日志里的真实报错（连接错误/401/代理），可能需在真机设 `HTTPS_PROXY`。

## 排障：WS 聊天"没有反应"（mode 强制 mock + 前端无加载指示）

用户点前端"模拟消费者手机端发言"（`BuyerSimulator.tsx` → `agentSocket.sendMessage` → WS `ws://localhost:8000/api/chat/stream/{id}`）后，副驾面板无任何输出。

- 根因 A：`main.py` WS 端点 `initial_state["mode"]` 被硬编码为 `"mock"`，即使用户配了 DeepSeek 也永远走 Mock、不调真实模型（之前一直没改）。已改为 `"auto"`（有 Key 真调，失败自动降级）。
- 根因 B（UX 缺口）：前端在 WS 分析期间**没有任何加载提示**。WS 链路从 `start` 到 `reply` 节点可能要数秒，期间面板不变 → 用户感知为"没反应"。`InsightPanel` 的 spinner 原本只在"重新生成/调整语气"（`isGenerating`）时显示，WS 主流程不触发。
- 已修复（前端）：`useUIStore` 新增 `analyzing`/`setAnalyzing`；`socket.ts` 收 `start`→setAnalyzing(true)、`done`/`error`→setAnalyzing(false)；`CopilotPane` 草稿区在 `isGenerating || analyzing` 时显示"正在分析买家消息..."。
- 沙箱实测（端口 8090，当前代码）：WS 探针连上后流式返回 12 帧（start + 10 节点 + done），`intent/emotion/summary/reply` 节点 `degraded=False` → **确认后端真调 DeepSeek 且完整跑通、不卡死**。
- 结论给用户：后端代码已验证可用，"没反应"基本是本机侧——(1) 未重启 uvicorn（旧代码仍跑）；(2) 真机连不上 `api.deepseek.com`（现会 ≤20s/节点后降级，不再永久挂起）；(3) 现已加加载指示，慢一点也能看见"分析中"。需重启后端 + 刷新前端。

## 排障：节点全跑完但"回复没生成"（前端展示 + 空回复防御）

用户重启后端后，日志显示 10 个节点全部执行完毕（context…fact_check），但仍看不到回复。排查：
- 沙箱探针实测（端口 8090）：reply 帧的 `reply_draft` 是**完整真实回复**（`degraded=false`），全链路 12 帧、DONE 正常 → 后端确定产出非空回复。
- `mock_reply`（fallback）也永远返回非空 → 后端任何情况下 reply 都非空。故"没回复"锁定在**前端展示/构建态**。
- 关键事实：AI 回复只写入**右侧副驾面板"回复草稿"**（`socket.ts` 仅 `setDraft`，不在聊天流加气泡）；S00015 自带初始草稿（mockData 第24行），模拟发言后应被**替换**。
- 前端链路核对无误：`socket.ts` 收 `node_update(node=reply, data.reply_draft)` → `useChatStore.setDraft(currentConversationId)`；`InsightPanel` 读 `drafts[c.id]` → 展示。id 一致（默认 S00015）。React StrictMode 双挂载由 `connect/disconnect` 逻辑兜住。

本轮加固（3 处）：
1. **后端** `app/agent/nodes/reply.py`：模型返回合法 JSON 但 `reply` 为空串时（前端以 `reply_draft` 空否决定回写），回退 `mock_reply` 并置 `degraded=True`，保证下发永不为空。已单测验证（空→mock，正常→原样）。
2. **前端** `src/services/socket.ts`：reply 到达即 `setDraft` + `setAnalyzing(false)` + `notify('已生成回复草稿')`（明确反馈）。
3. **前端** `src/features/Copilot/CopilotPane.tsx`：加载态改为 `isGenerating || (analyzing && !remoteDraft)` —— 拿到草稿就立即展示，**分析态不再盖住已有草稿**（此前 `analyzing` 卡住会一直显示"正在分析…"而看不到草稿）。
