# 知微客服副驾初赛 Demo 开发任务

## 1. 项目边界

### 1.1 已确认条件

| 项目 | 决策 |
| --- | --- |
| 开发周期 | 1 个月，按 20 个工作日规划 |
| 团队 | 3 人：前端 1 人，后端 2 人 |
| 目标 | 初赛可运行 Demo、演示视频、PPT 所需真实链路 |
| 前端 | React，按客服工作台示意图复刻三栏布局 |
| 模型 | 首选阿里云百炼，采用可替换模型网关 |
| 数据 | 以官方 Excel 为主，支持聊天、订单和 5 类工单的关联 |
| 核心能力 | 客服副驾为主体，不良反应处置和服务承诺跟踪为两个标志性能力 |

### 1.2 初赛必须完成

Demo 必须能够在真实浏览器中完成以下闭环：

1. 选择一个消费者会话。
2. 展示聊天上下文、关联订单、历史服务轨迹和工单状态。
3. 调用 Agent 识别意图、情绪、风险和缺失信息。
4. 生成有事实依据的回复草稿，客服可以编辑并确认。
5. 对不良反应场景进行分级、收集信息、创建专项工单并安排回访。
6. 从客服回复中抽取服务承诺，计算截止时间并进入履约队列。
7. 在履约雷达中展示临近到期、已超时和已履约状态。
8. 所有关键结论能够回溯到聊天、订单、工单或规则证据。

### 1.3 初赛暂不做

- 生产级多店铺权限和真实电商平台写操作。
- 大规模商品知识库和商品推荐系统。
- 模型微调。
- 复杂的批次统计建模。
- 全量客服绩效管理。
- 真实支付、退款、打款和医疗费用执行。

这些内容可以放入答辩中的未来规划，但不应挤占 Demo 核心闭环。

## 2. 推荐技术方案

### 2.1 总体架构

```text
React + TypeScript + Vite
          ↓ REST / SSE
FastAPI API 服务
          ↓
会话服务  订单服务  工单服务  承诺引擎  Agent 编排器
          ↓              ↓
SQLite/PostgreSQL      百炼模型网关
          ↓              ↓
官方 Excel 导入       文本模型 / 视觉模型
```

### 2.2 技术选型

| 层 | 建议选型 | 说明 |
| --- | --- | --- |
| 前端 | React、TypeScript、Vite | 适合快速迭代和现场演示 |
| UI | CSS Modules 或 Tailwind CSS | 复刻示意图，不引入过重组件库 |
| 图标 | Lucide React | 统一线性图标风格 |
| 数据请求 | TanStack Query | 处理缓存、加载、错误和重试 |
| 状态 | Zustand | 管理当前会话、插件 Tab 和 Demo 状态 |
| 后端 | Python FastAPI | 便于数据处理、模型调用和评测脚本复用 |
| 数据库 | SQLite 起步，保留 PostgreSQL 兼容性 | 初赛单机 Demo 足够，避免部署复杂度 |
| Agent | 自研有向状态机 | 节点可控、易调试，初赛不需要多 Agent 自由协作 |
| 模型接入 | 百炼 OpenAI 兼容接口或官方 SDK | 封装为 `ModelGateway`，便于换模型 |
| 异步任务 | FastAPI BackgroundTasks 或 APScheduler | 承诺扫描规模小，不必先引入 Celery |
| 测试 | Pytest、Vitest、Playwright | 分别覆盖后端、前端和关键演示流程 |

### 2.3 百炼接入建议

当前不把具体模型名称写死在业务代码里。百炼控制台的可用模型、计费和上下文限制可能变化，项目通过环境变量配置：

```env
DASHSCOPE_API_KEY=
DASHSCOPE_BASE_URL=
MODEL_FAST=
MODEL_REASONING=
MODEL_VISION=
MODEL_EMBEDDING=
```

建议准备三档模型槽位：

- `MODEL_FAST`：意图、实体、情绪、承诺抽取等短任务。
- `MODEL_REASONING`：跨会话轨迹摘要、风险判断、回复草稿和高风险复核。
- `MODEL_VISION`：图片类型、清晰度、批次号、票据字段和可见现象描述。

模型名称由百炼控制台当前可用模型填入，不在代码和 PPT 中固定版本。上线前用同一评测集测试质量、延迟、输入输出 Token 和单会话成本，再确定默认模型。

推荐的路由策略：

```text
普通短消息 → FAST
跨订单/工单或情绪升级 → REASONING
含图片 → VISION
L2/L3 不良反应 → REASONING + 规则复核
模型超时或配额不足 → 结构化 Mock 结果，不阻断 Demo
```

不建议为了初赛 Demo 引入微调。官方样本量只有 138 个会话，优先做提示约束、工具查询、结构化输出和按会话隔离评测。

官方实时价格页面本轮无法稳定访问，因此具体单价必须以百炼控制台和当前官方价格页为准。项目应实现成本日志，并在答辩前记录：每个模型调用的 Token、耗时、错误、缓存命中和单会话成本。

### 3.2 后端工程师 A：数据与业务服务

负责人：Excel 导入、统一数据模型、业务 API、承诺状态机和 Demo 数据。

- 清洗官方 Excel 并导入数据库。

- 建立固定演示数据和重置接口，确保现场可重复运行。

### 3.3 后端工程师 B：Agent 与评测

负责人：百炼网关、Agent 工作流、提示词、风险规则、评测和成本日志。

- 封装百炼文本、视觉和 Embedding 调用。
- 实现结构化 JSON Schema 输出和失败重试。
- 实现会话理解、轨迹摘要、风险判断和回复草稿节点。
- 实现不良反应专项 Agent。
- 实现承诺抽取和时间表达归一化。
- 建立人工标注金标准和离线评测脚本。
- 记录模型调用、Token、延迟、失败和人工修改。

### 3.4 三人共同责任

- 产品流程和字段定义必须共同评审。
- 每天用同一 Demo 数据跑一次端到端流程。
- 所有外部模型结果必须允许 Mock，保证断网或配额异常时可演示。
- PPT 和视频只使用已经能在 Demo 中复现的能力。

## 7. 接口契约

### 7.1 获取客服副驾

### 7.3 动作确认

任何会改变工单或承诺状态的动作必须先预览，再确认：

```text
POST /api/actions/preview

```

确认接口需要携带 `action_id`、`operator_id`、`idempotency_key` 和人工确认时间，避免重复建单。

## 8. 前端视觉还原规范

按 Word 文档中的客服工作台图片执行，不把界面做成营销 Dashboard：

- 左侧深色窄导航，使用图标和短标签。
- 第二列是浅灰背景的会话列表，当前会话用暖色选中线。
- 中部为白色聊天区，顶部显示消费者和关联对象，消息气泡保持紧凑。
- 右侧为白色插件区，顶部使用蓝色或暖色状态条，内容按“判断、事实、动作、回复”排列。
- 页面整体采用浅灰、白色、深灰和珊瑚色作为主色，风险色只用于状态。
- 卡片圆角控制在 8 至 12px，不堆叠过多装饰性卡片。
- 1440×900 是首要演示分辨率，1280×800 是最低适配分辨率。
- 关键动作使用图标加文字；纯图标按钮必须有 tooltip。
- 右侧插件不能遮挡聊天输入区，所有文本必须在面板内完整换行。

## 9. 质量门槛

### 9.1 产品验收

- 普通场景、L3 不良反应、承诺到期各有一条可重复演示路径。
- 所有模型结果带证据或明确标记待核实。
- 发送前可编辑，敏感动作需要确认。
- 工单和承诺的状态变化能反映到后续查询。

### 9.2 模型验收

- 高风险召回率优先于总体准确率。
- 金额、订单号、状态和截止时间不能凭空生成。
- 不良反应场景不能输出诊断或替代医生建议。
- 承诺抽取只对最终发送消息生效。

### 9.3 工程验收

- 无 API Key 时可使用 MockProvider 完成完整 Demo。
- 百炼超时、限流或错误时，前端显示降级状态而不是空白。
- `POST /api/demo/reset` 可在 3 秒内恢复演示数据。
- README 能指导新环境完成安装、导入、启动和演示。
- 最终压缩包不包含 `.env`、API Key、个人信息和临时调试文件。

## 10. 初赛演示顺序

建议控制在 4 分钟：

1. **30 秒**：从客服工作台进入 `魏h**`，展示历史承诺未完成和跨会话轨迹。
2. **60 秒**：查看订单与工单事实，采纳回复草稿，预览并确认催办动作。
3. **90 秒**：切换到 `S00015`，展示已就医触发 L3、资料待识别、专项建单和回访承诺。
4. **50 秒**：切换到履约雷达，展示退款、回访、补发三类承诺，模拟一次超时和一次履约。
5. **30 秒**：展示评测、成本日志和降级能力，说明系统如何保证不虚构事实。
