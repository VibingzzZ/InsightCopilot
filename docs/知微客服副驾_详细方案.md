# 知微客服副驾详细方案

## 1. 项目概述

### 1.1 项目名称

**知微客服副驾**

副标题：面向美妆电商人工客服的全轨迹服务与风险闭环智能体

### 1.2 一句话定位

在客服现有工作台右侧提供一个由人工确认的 AI 副驾，实时汇总消费者完整服务轨迹，识别诉求和风险，给出有依据的回复与操作建议，并通过“不良反应处置”和“服务承诺跟踪”确保高风险问题真正闭环。

### 1.3 核心判断

本项目不把重点放在自动回复数量上，而是解决人工客服的三个实际问题：

1. **看不清**：订单、历史聊天和不同类型工单分散在多个系统中，客服无法快速还原发生过什么。
2. **判不准**：客服很难同时判断消费者意图、情绪变化、业务规则和潜在风险。
3. **跟不住**：客服在聊天中承诺的退款、回访、补发和核实事项缺少统一跟踪，换班后容易失联或超时。

系统最终形成以下服务闭环：

```text
消费者发起咨询
    ↓
识别身份、订单和当前诉求
    ↓
整合历史会话、订单与工单
    ↓
判断风险并核验业务事实
    ↓
生成回复建议和下一步动作
    ↓
客服确认后执行
    ↓
自动记录承诺并跟踪履约
    ↓
完成、回访或升级处理
```

## 2. 赛题与数据洞察

### 2.1 与赛题要求的对应关系

| 赛题考察方向 | 本方案的对应设计 |
| --- | --- |
| 核心功能完整性与实用性 | 嵌入现有工作台右侧插件区，覆盖识别、查询、回复、建单、跟踪和主管处置 |
| 多源跨维度融合 | 以会话 ID、订单号、工单号和消费者身份关联聊天、订单与五类工单 |
| 大模型智能分析准确度 | 建立意图、风险、信息抽取、承诺抽取、回复质量和事实一致性评测集 |
| AI Agent 工作流 | 使用受控工作流调用订单、工单、知识库和任务工具，由客服确认高影响动作 |
| 多模态能力 | 处理破损、错发、少件、退款截图和不良反应资料图片，并判断图片是否足以支持后续流程 |
| 技术创新与场景价值 | 将“共情”从回复风格延伸为风险识别、事实解释和承诺履约 |
| 性能与成本优化 | 小模型优先、规则预筛、上下文压缩、缓存复用，复杂场景才调用较大模型或视觉模型 |

### 2.2 官方数据基线

现有业务数据包括 998 条消息、138 个完整会话、113 个订单和 80 个工单。会话覆盖 10 个一级场景和 41 个二级场景，平均每个会话 7.23 条消息。

关键特征如下：

- 113 个会话关联订单，约占全部会话的 81.9%。
- 80 个会话关联工单，约占全部会话的 58.0%。
- 29 个会话包含图片，可用于展示多模态证据处理。
- 按昵称统计，24 位消费者存在重复进线，共涉及 50 个会话。
- 80 个工单中有 28 个仍处于进行中、处理中或待处理状态，占 35%。
- 工单包括补发换货 24 条、线下打款 13 条、物流 15 条、不良反应 10 条和售后退货 18 条。

这些数据天然支持“完整服务轨迹”和“跨会话履约跟踪”。数据量较小且相似话术较多，因此原始数据更适合用作评测基线和少样本示例，不建议将微调作为作品的主要创新点。

## 3. 目标用户与业务目标

### 3.1 目标用户

| 用户    | 主要需求               | 系统提供的能力                  |
| ----- | ------------------ | ------------------------ |
| 一线客服  | 快速理解问题并给出准确、有温度的处理 | 当前诉求、轨迹摘要、风险提示、回复草稿、操作建议 |
| 客服组长  | 发现高风险会话和即将超时事项     | 风险队列、承诺履约看板、升级与分派        |
| 售后专员  | 获得完整证据并减少重复询问      | 自动收集字段、图片检查、标准工单草稿       |
| 运营与质检 | 了解问题来源和服务质量        | 场景分布、风险趋势、超时原因、回复质量与证据追溯 |

### 3.2 业务目标

首版系统聚焦以下四个可验证目标：

- 减少客服在不同系统之间查询和复制信息的时间。
- 降低重复询问订单、症状、图片和退款信息的次数。
- 提高不良反应、投诉倾向和重复进线等风险的召回率。
- 降低客服承诺超时和消费者因未履约再次进线的比例。

## 4. 产品总体设计

### 4.1 产品形态

系统采用“工作台右侧插件 + 主管风险看板”两种界面。

右侧插件遵循官方客服工作台的现有布局，不改变左侧客户列表和中部聊天流程。插件默认宽度保持稳定，按客服处理顺序展示信息，避免堆放大量卡片。

### 4.2 右侧插件信息结构

#### 顶部状态区

- 当前风险等级：普通、关注、高风险、紧急。
- 当前一级和二级意图。
- 识别置信度和证据来源。
- “展开完整轨迹”入口。

#### 当前问题区

- 消费者现在要解决什么。
- 已确认事实：订单、商品、金额、状态、时间。
- 仍缺少的信息：例如破损照片、批次号、症状出现时间。
- 冲突信息：例如消费者描述与订单或工单状态不一致。

#### 建议处置区

- 推荐下一步动作，按优先级排列。
- 可调用工具：查询物流、创建工单、催办、升级、登记回访。
- 每项动作显示原因、影响和是否需要客服确认。

#### 回复草稿区

- 默认提供一条简洁回复。
- 支持“更简洁”“更正式”“加强安抚”等调整。
- 回复中的订单状态、金额、时间和处理结果必须显示证据标记。
- 客服可编辑、确认和发送，系统不得自动发送高风险回复。

#### 承诺区

- 当前会话新识别的承诺。
- 历史未完成承诺和截止时间。
- 责任人、关联工单、剩余时间和履约证据。

### 4.3 主管风险看板

主管看板以“需要采取行动的事项”为中心，避免只展示统计图表。

主要视图包括：

- 紧急不良反应事件。
- 消费者再次进线但原承诺尚未完成的事件。
- 两小时内到期、当日到期和已经超时的承诺。
- 相同产品或批次出现的异常聚集。
- 等待人工确认、跨团队阻塞和缺少证据的事项。

筛选条件包括风险等级、场景、责任团队、处理人、承诺状态、商品和批次。主管可在看板中完成分派、催办、升级、添加备注和确认关闭。

## 5. 日常接待副驾

日常接待副驾是系统的主体，负责所有场景的通用处理。

### 5.1 会话理解

每收到一条新消息，系统更新以下结构化状态：

- 一级场景和二级场景。
- 显性诉求与隐含诉求。
- 订单号、商品、金额、时间、物流号等实体。
- 当前情绪、情绪变化方向和触发原因。
- 已经完成、正在处理和下一步待办。
- 风险信号及其原文证据。

情绪判断不只输出“正面或负面”，而是提供客服能采取行动的信息。例如：

```json
{
  "emotion": "焦虑",
  "trend": "上升",
  "trigger": "退款超过承诺时间仍未到账",
  "evidence": "都一个礼拜了一分没到，急死了",
  "recommended_response": "先承认延误，再说明核验结果和新的确定时间"
}
```

### 5.2 全轨迹摘要

系统以消费者、会话、订单和工单之间的关系生成服务轨迹，摘要遵循“事实、进展、待办、风险”的固定格式。

示例：

```text
消费者曾有 2 次相关服务记录。
5 月 5 日咨询退款延迟，客服承诺 3 个工作日内完成核实。
关联线下打款工单仍在进行中，尚无到账记录。
本次为再次进线，情绪从焦虑升级为不满。
建议先催办财务，再向消费者说明当前进度和明确回访时间。
```

摘要只保留当前任务相关的历史信息，避免将全部聊天记录发送给模型。

### 5.3 事实核验与回复生成

回复生成遵循“先查事实、后写回复”的原则：

1. 从消息中识别订单号或选择可能相关的订单。
2. 调用订单、物流和工单查询工具。
3. 检索适用的业务规则和标准流程。
4. 生成包含事实、共情、处理动作和预期时间的回复草稿。
5. 对金额、时间、状态和政策逐项校验。
6. 客服确认后发送。

如果工具没有返回事实，模型必须明确标记“待核实”，不能编造答案。

### 5.4 一键操作

系统根据场景显示有限的合法动作：

- 创建补发或换货工单。
- 创建线下打款工单。
- 创建物流异常工单。
- 创建不良反应工单。
- 创建退货处理工单。
- 催办、升级、登记回访和关闭任务。

Agent 负责预填字段，客服负责核验并确认。金额打款、退款批准、医疗费用处理和异常退货等高影响动作必须二次确认。

## 6. 标志性能力一：不良反应处置

### 6.1 设计目标

当消费者描述泛红、刺痛、瘙痒、肿胀、起疹、爆痘或已经就医时，系统应尽快识别风险，指导客服收集必要信息，并建立可跟踪的处置任务。

系统提供的是服务风险分级和流程辅助，不做医学诊断，不根据图片判断疾病，也不替代医生建议。

### 6.2 触发条件

以下任一条件可触发不良反应工作流：

- 文本出现症状、就医、药物、赔偿或监管投诉等信号。
- 图片或文档疑似包含皮肤异常、门诊记录或费用票据。
- 历史不良反应工单尚未关闭。
- 同一消费者再次进线并报告症状加重。
- 同一商品或批次在一定时间窗口内出现多条相关记录。

规则召回和模型语义判断并行运行。规则负责兜底明显关键词，模型负责理解口语、否定和上下文。

### 6.3 风险分级

| 等级 | 判断示例 | 系统动作 |
| --- | --- | --- |
| L0 普通咨询 | 询问敏感肌是否适用，但没有实际不适 | 提供成分与试用注意事项，禁止保证“绝不过敏” |
| L1 轻度不适 | 轻微泛红、刺痒或局部小颗粒，尚未加重 | 建议停止使用并收集信息，建立普通回访任务 |
| L2 明显不适 | 范围扩大、持续加重、明显红肿或消费者强烈焦虑 | 提示及时寻求专业医疗帮助，创建高优先级工单并升级专员 |
| L3 紧急事件 | 已就医、呼吸不适、眼部严重异常、住院或提出监管投诉 | 立即升级主管和专项团队，限制普通客服自由回复，启动持续跟踪 |

分级结果必须显示触发依据，并允许客服或主管调整。L2 和 L3 不得由系统自动降级。

### 6.4 信息收集清单

系统从历史聊天、订单和图片中自动回填，缺失项才提示客服询问：

- 消费者年龄和自述肤质。
- 使用商品、订单、产品批次号。
- 使用部位和使用方式。
- 症状描述、出现时间和变化趋势。
- 是否停止使用、是否就医。
- 是否有其他新产品、医美或已知过敏因素。
- 图片、门诊资料和费用票据是否完整、是否清晰。
- 消费者当前诉求：咨询、退货、退款、医疗费用或其他处理。

系统必须避免重复询问已经存在于聊天或工单中的字段。

### 6.5 多模态处理

视觉模型只完成与服务流程有关的任务：

- 判断上传内容属于皮肤照片、商品照片、门诊材料还是费用票据。
- 检查图片是否清晰、是否完整、关键区域是否被遮挡。
- 提取票据日期、金额和机构名称等可核验字段。
- 识别商品批次号和包装信息。
- 对皮肤照片仅描述可见现象，例如“局部发红区域可见”，不输出病名和病因。

低清晰度或不确定结果必须要求人工确认。

### 6.6 不良反应 Agent 流程

```text
症状或资料触发
    ↓
查询订单、商品与历史不良反应记录
    ↓
提取症状、时间、部位、批次和就医状态
    ↓
规则与模型共同分级
    ↓
生成安全回复及待询问字段
    ↓
客服确认并创建不良反应工单
    ↓
创建回访承诺和责任人
    ↓
检查恢复、退款及费用处理状态
    ↓
关闭或升级
```

### 6.7 批次聚集预警

当同一商品或批次在指定时间窗内出现多条 L1 以上记录，系统产生聚集预警。聚集规则由企业配置，例如“7 天内同一批次出现 3 条以上不良反应记录”。

预警包含事件数量、症状分布、地区、首次和最近发生时间。系统只提示调查，不直接推断产品存在质量问题。

## 7. 标志性能力二：服务承诺跟踪

### 7.1 设计目标

系统将聊天中容易遗忘的自然语言承诺转换为可追踪任务，持续检查工单和业务状态，在到期前提醒，在超时或消费者再次进线时升级。

可识别的承诺包括：

- 发货、补发和换货时间。
- 退款或线下打款到账时间。
- 物流核实和仓库反馈时间。
- 电话回访和消息回复时间。
- 优惠券、赠品和补偿发放。
- 专员或主管处理结果。

### 7.2 承诺结构

每项承诺使用统一数据结构：

```json
{
  "promise_id": "P-20260505-001",
  "session_id": "S00015",
  "customer_id": "消费者脱敏标识",
  "order_id": "关联订单号",
  "ticket_id": "关联工单号",
  "promise_type": "电话回访",
  "promise_text": "专员明天上午会致电回访",
  "created_at": "2026-05-05T20:18:00+08:00",
  "deadline": "2026-05-06T12:00:00+08:00",
  "owner_team": "不良反应专员组",
  "owner": null,
  "verification_rule": "存在回访记录且状态为已完成",
  "risk_level": "高",
  "status": "active",
  "evidence_message_id": "原消息ID"
}
```

### 7.3 时间归一化

大模型负责识别“明天上午”“今天下班前”“1 至 3 个工作日”等表达，确定性时间服务负责计算实际截止时间。

时间服务需要支持：

- 会话所在地时区。
- 工作日、周末和企业节假日日历。
- “48 小时”和“2 个工作日”的区别。
- 时间范围的最早提醒时间和最晚截止时间。
- 原承诺变更后的版本记录。

无法确定的表述，例如“尽快”“晚点回复”，必须提示客服补充明确时间，不能自行生成虚假截止时间。

### 7.4 状态机

```text
识别待确认
    ↓ 客服确认
生效
    ↓
临近到期
    ↓
已超时

任一有效状态可在证据满足后进入“已履约”
确需变更时进入“已变更”，保留原承诺和变更原因
消费者取消诉求时进入“已取消”，由客服确认
```

系统不能仅凭客服发送“已经处理”就认定履约，需要检查对应证据。例如：

- 补发承诺：补发工单已创建且存在物流单号。
- 退款承诺：退款或转账状态为已完成。
- 回访承诺：存在符合时间要求的回访记录。
- 物流核实：工单中已有明确处理结果。
- 优惠券承诺：权益系统返回发放成功。

### 7.5 提醒与升级

| 触发事件 | 系统处理 |
| --- | --- |
| 临近到期 | 提醒责任人，展示还缺少的动作或证据 |
| 已超时 | 提升风险等级并进入主管看板 |
| 消费者再次进线 | 在客服插件顶部展示历史未履约承诺，优先处理 |
| 高风险承诺临近到期 | 同时提醒责任人和组长 |
| 工单被关闭但承诺未满足 | 标记状态冲突，禁止自动关闭 |
| 多次修改承诺时间 | 标记为服务风险并要求主管确认 |

### 7.6 与共情的关系

当消费者再次进线时，系统应先承认已有记录，而不是让消费者重新解释。例如：

```text
很抱歉让您再次联系。上次登记的退款核实还没有完成，我已经看到对应工单，当前正在财务处理。我先为您加急，并在今天 18:00 前向您回复明确结果。
```

这条回复的价值来自对历史事实的理解和对后续行动的负责，而不只是使用更温和的语气。

## 8. 风险识别体系

### 8.1 风险信号

风险由四类信号共同决定：

- **内容风险**：不良反应、就医、疑似欺诈、监管投诉、舆情曝光。
- **情绪风险**：负面情绪持续上升、明确威胁投诉、强烈不信任。
- **流程风险**：工单超时、状态冲突、证据缺失、跨团队无人认领。
- **关系风险**：重复进线、重复退款、同类问题多次发生、历史承诺未履约。

### 8.2 风险评分

评分用于排序，不直接替代业务规则。建议采用可解释的加权方式：

```text
风险分 = 场景严重度
       + 情绪升级分
       + 重复进线分
       + 承诺超时分
       + 工单阻塞分
       + 特殊规则加分
```

医疗紧急信号、明确监管投诉和重大舆情信号使用硬规则直接提升到高风险或紧急等级。每次评分必须保留触发证据、规则版本和模型版本。

### 8.3 风险处置原则

- 高召回优先，但所有高风险提示都要给出具体证据。
- 不因消费者历史退款多就自动判定欺诈。
- 不把情绪强烈等同于恶意。
- 风险标签不得直接暴露给消费者。
- 人工可调整风险等级，调整需要记录理由。

## 9. Agent 系统设计

### 9.1 设计原则

系统采用单一编排器驱动的受控工作流。各节点职责固定，输出结构化数据，避免多个自由 Agent 相互讨论造成成本和不确定性。

### 9.2 工作流节点

| 节点 | 输入 | 输出 | 实现方式 |
| --- | --- | --- | --- |
| 会话状态更新 | 新消息、当前状态 | 意图、实体、情绪、缺失信息 | 文本模型结构化输出 |
| 身份与关系解析 | 昵称、订单号、会话 ID | 相关订单、历史会话、工单 | 确定性数据库查询 |
| 轨迹压缩 | 多源记录 | 当前任务相关摘要 | 规则筛选加模型摘要 |
| 风险判断 | 当前会话、历史、工单 | 风险等级、原因、证据 | 规则与分类模型融合 |
| 专项流程路由 | 意图、风险 | 普通、不良反应、退款等流程 | 确定性状态机 |
| 工具调用 | 业务动作 | 查询结果或工单草稿 | 白名单工具接口 |
| 回复生成 | 事实、规则、动作 | 回复草稿 | 文本模型 |
| 事实校验 | 草稿、工具结果 | 通过、修订或阻断 | 字段级校验加模型审查 |
| 承诺抽取 | 客服草稿和最终消息 | 承诺结构 | 模型抽取加时间服务 |
| 履约监控 | 承诺、工单状态 | 提醒、履约或升级 | 定时任务与确定性规则 |

### 9.3 结构化输出约束

所有模型节点使用 JSON Schema 约束输出，关键结论包含证据位置和置信度。示例：

```json
{
  "intent": {
    "major": "不良反应",
    "minor": "过敏就医",
    "confidence": 0.96,
    "evidence_message_ids": ["m1", "m3"]
  },
  "risk": {
    "level": "L3",
    "reasons": ["消费者已就医", "提及监管投诉"],
    "evidence_message_ids": ["m1", "m3"]
  },
  "missing_fields": ["产品批次号"],
  "recommended_actions": ["升级不良反应专员", "创建24小时回访任务"]
}
```

JSON 校验失败时只重试当前节点，不重新运行完整工作流。

### 9.4 模型与工具分工

大模型适合处理：

- 口语化意图、情绪和上下文理解。
- 长会话摘要和相关历史筛选。
- 图片类型识别及资料字段提取。
- 回复草稿和承诺语义抽取。

确定性程序负责：

- 查询订单、金额、物流和工单状态。
- 截止时间计算和节假日处理。
- 权限、状态机和风险硬规则。
- 承诺履约验证。
- 日志、版本和审计。

建议采用比赛当期可用的通义千问开源文本模型和视觉模型作为底座。最终型号根据显存、准确度和演示环境压测结果确定，避免在方案阶段锁定可能不适配现场设备的参数规模。

## 10. 数据与知识架构

### 10.1 官方数据映射

| 数据表 | 系统用途 |
| --- | --- |
| 聊天记录 | 会话重建、意图识别、情绪变化、承诺抽取和回复评测 |
| 订单 | 核验商品、金额、状态、发货、赠品、物流及买家留言 |
| 补发换货工单 | 核验补发、换货、色号、数量、物流和完成状态 |
| 线下打款工单 | 跟踪运费、价保、退款差额及转账状态 |
| 物流工单 | 跟踪停滞、丢件、破损、少件和改址问题 |
| 不良反应工单 | 记录肤质、症状、发生时间、批次、停用、就医和回访状态 |
| 售后退货工单 | 核验退货原因、异常标记、物流和退款处理 |

### 10.2 核心业务对象

建议建立以下核心表：

- `customer_profile`：消费者脱敏标识、偏好和风险注意事项。
- `conversation`：会话状态、意图、摘要、风险等级。
- `message`：原始消息、角色、内容类型、时间和证据索引。
- `order`：订单事实镜像。
- `service_ticket`：统一工单索引，保留各类工单扩展字段。
- `service_event`：会话、订单和工单形成的时间线事件。
- `promise`：承诺内容、截止时间、责任人、状态和验证规则。
- `risk_event`：风险类型、等级、证据、处理记录和关闭原因。
- `knowledge_item`：业务规则、标准流程、版本和生效时间。
- `agent_trace`：模型输入摘要、输出、工具调用和人工修改记录。

### 10.3 知识库

知识库优先收录可执行规则，而不是大量营销文案：

- 售前咨询与产品使用注意事项。
- 价保、退款、退货和运费规则。
- 补发、换货和物流异常流程。
- 不良反应客服处置规范。
- 客服可承诺的时间范围和权限边界。
- 投诉、舆情和异常退款升级规则。

检索结果必须带文档版本和生效日期。回复生成只能引用当前有效规则。

## 11. 技术架构与实现建议

### 11.1 系统组件

```text
Web 客服工作台插件 / 主管看板
             ↓
        API 网关与鉴权
             ↓
       Agent 工作流服务
      ↙       ↓        ↘
模型推理服务  业务工具层  风险与承诺引擎
      ↓       ↓        ↓
向量检索   订单/工单库  定时任务与事件队列
             ↓
       审计日志与评测平台
```

### 11.2 Demo 技术栈

- 前端：React 或 Vue，复刻工作台三栏结构，重点实现右侧插件和主管看板。
- 后端：FastAPI，提供会话、订单、工单、Agent 和承诺接口。
- 工作流：LangGraph 或自研有向状态机。
- 数据库：演示阶段使用 PostgreSQL；单机快速演示可使用 SQLite。
- 检索：小规模知识库可使用 FAISS，大规模部署可替换为 Elasticsearch 或向量数据库。
- 模型服务：vLLM 或兼容 OpenAI 接口的本地推理服务。
- 异步任务：Celery 与 Redis，或使用轻量定时任务完成承诺扫描。
- 可观测性：记录每个节点耗时、Token、工具结果、模型输出和人工修改。

### 11.3 核心接口

| 接口 | 功能 |
| --- | --- |
| `POST /sessions/{id}/messages` | 接收新消息并更新会话状态 |
| `GET /sessions/{id}/copilot` | 获取轨迹摘要、风险、建议和回复草稿 |
| `POST /sessions/{id}/actions/preview` | 生成建单、催办或升级草稿 |
| `POST /sessions/{id}/actions/confirm` | 客服确认后执行动作 |
| `POST /messages/{id}/reply-draft` | 生成或改写回复 |
| `POST /promises/extract` | 从最终客服消息中抽取承诺 |
| `PATCH /promises/{id}` | 确认、修改、分派或取消承诺 |
| `GET /risk-queue` | 获取主管风险队列 |
| `GET /customers/{id}/timeline` | 获取消费者服务时间线 |

### 11.4 权限与安全

- 客服只能查看和操作自己权限范围内的订单与工单。
- 支付宝账号、手机号、地址等敏感字段默认脱敏。
- 敏感字段不进入大模型上下文，线下打款通过受控表单和工具传递。
- 所有模型建议、人工修改和操作结果均保留审计记录。
- 高影响动作需要二次确认，系统不自动退款、不自动打款、不自动给出医疗诊断。

## 12. 模型成本与性能优化

### 12.1 模型路由

- 普通短会话：小型文本模型完成意图、实体和回复。
- 长会话或复杂跨工单场景：较大文本模型生成轨迹摘要和处置建议。
- 只有收到图片时调用视觉模型。
- 不良反应、监管投诉等高风险场景启用更严格的复核节点。

### 12.2 Token 优化

- 先用订单号、会话 ID 和场景筛选数据，再交给模型。
- 历史记录压缩成结构化事件，不重复发送原始全文。
- 商品规则和流程按段落检索，只传递相关内容。
- 复用同一轮已经查询的订单和工单结果。
- 将稳定的系统提示、Schema 和知识片段缓存。
- 普通会话不运行视觉模型和第二次大模型审查。

### 12.3 性能目标

以下为开发目标，不是当前已测结果：

- 普通文本场景首屏建议 P95 小于 3 秒。
- 包含多源轨迹的复杂场景 P95 小于 6 秒。
- 承诺扫描不影响在线接待链路。
- 普通场景单会话模型调用不超过 2 次。
- 高风险场景允许增加一次复核，以准确性优先。

## 13. 评测方案

### 13.1 数据划分

官方数据存在同类模板话术，随机按消息切分会造成训练和测试泄漏。应执行以下规则：

1. 以完整会话为最小切分单位。
2. 对相似话术或同一场景模板聚类，同簇只进入一个数据集。
3. 同一消费者的关联会话尽量放入同一数据集。
4. 保留一组不做提示调优的隐藏测试集。
5. 合成数据只进入训练或压力测试，不进入官方原始数据测试结果。

### 13.2 金标准标注

建议对 138 个会话进行双人标注，分歧由第三人确认。标注内容包括：

- 一级和二级意图。
- 当前诉求与必要字段。
- 情绪类型、强度、变化和触发原因。
- 风险类型、等级和证据消息。
- 正确处理动作与禁止动作。
- 客服承诺、截止时间和验证条件。
- 回复中的事实、共情、可执行性和合规性。

### 13.3 离线指标

| 能力 | 指标 | 建议验收目标 |
| --- | --- | --- |
| 一级意图 | Macro-F1 | 不低于 0.90 |
| 二级意图 | Macro-F1 | 不低于 0.82 |
| 订单号、金额、症状等实体 | 字段级 F1 | 不低于 0.92 |
| 高风险识别 | Recall | 不低于 0.92 |
| 高风险识别 | Precision | 不低于 0.80 |
| 承诺识别 | F1 | 不低于 0.88 |
| 承诺截止时间 | Exact Match 或允许误差内准确率 | 不低于 0.90 |
| 事实一致性 | 有依据事实占全部事实的比例 | 不低于 0.98 |
| 工具选择 | 正确工具调用率 | 不低于 0.95 |
| 不良反应安全性 | 严重漏报与违规建议数量 | 隐藏测试集为 0 |

这些数值是项目验收目标，答辩时只展示真实测试结果，不能把目标值表述为已经达到的成绩。

### 13.4 人工盲评

邀请客服或模拟客服对原始工作方式和副驾方式进行盲评：

- 是否正确理解消费者问题。
- 是否减少重复询问。
- 回复是否自然且有针对性。
- 处理动作是否符合业务规则。
- 是否能明确下一步和完成时间。

每条回复采用 1 至 5 分量表，并记录人工修改比例。人工修改比例比单纯的“采纳率”更能反映草稿质量。

### 13.5 业务模拟指标

- 首次有效回复用时。
- 单会话查询系统次数。
- 建单字段缺失率。
- 高风险发现提前量。
- 承诺超时率。
- 因未履约导致的再次进线率。
- 单会话 Token 和推理成本。

## 14. 核心演示脚本

### 14.1 演示一：重复进线与未完成事项

选择存在多次进线的消费者作为演示对象。例如数据中的 `魏h**` 曾出现退款延迟、空包裹争议和催发货三次不同会话。

演示步骤：

1. 消费者发来“上次答应处理的退款怎么还没到”。
2. 插件立即展示历史退款会话、关联订单和仍未完成的处理事项。
3. 系统识别“再次进线 + 历史承诺未完成”，风险升级。
4. Agent 查询线下打款或退款状态，而不是要求消费者重新提供订单号。
5. 插件生成有历史意识的回复草稿和催办动作。
6. 客服确认催办，并承诺在当日具体时间前反馈。
7. 新承诺自动进入履约雷达。

该演示证明系统能够跨会话记住服务事实，同时避免根据历史争议直接把消费者标记为恶意。

### 14.2 演示二：不良反应就医

以 `S00015` 的过敏就医场景为基础：

1. 消费者描述红肿刺痛并表示已经在医院。
2. 系统触发 L3 风险，显示原文证据和必须立即执行的动作。
3. 消费者上传门诊资料，视觉模型识别资料类型和可提取字段。
4. 插件自动回填订单、商品、症状和就医状态，仅提示询问缺少的批次号等信息。
5. 系统生成安全回复，避免医学诊断和不恰当用药建议。
6. 客服确认后创建不良反应专项工单、退款任务和次日上午回访承诺。
7. 主管看板出现高风险事件，直到工单、费用处理和回访均满足条件才允许关闭。

### 14.3 演示三：主管履约看板

1. 展示所有临近到期和已经超时的承诺。
2. 打开一条“1 至 3 个工作日到账”的线下打款承诺。
3. 显示承诺原文、时间归一化结果、责任人和工单状态。
4. 模拟工单更新为已完成，系统检查到账证据并自动标记履约。
5. 模拟工单关闭但无履约证据，系统提示状态冲突并要求人工处理。

完整演示建议控制在 4 至 5 分钟，其中前两段占主要时间，看板只展示关键闭环。

## 17. 方案差异化

### 17.1 与普通话术助手的区别

普通话术助手根据最后一句话生成回复。知微客服副驾先查询业务事实、理解历史轨迹、判断风险，再给出可以执行并可追踪的建议。

### 17.2 与传统工单系统的区别

传统工单需要客服手动填写，且通常从建单后才开始记录。系统从对话中自动发现事件、预填字段、保留证据，并跟踪消费者在聊天中得到的具体承诺。

### 17.3 与普通 SLA 看板的区别

SLA 管理某类业务的统一时限。承诺雷达管理某位客服在某次会话中对某位消费者作出的具体承诺，并通过订单或工单结果验证是否完成。

### 17.4 最有价值的创新点

本方案把“服务共情”定义为四个可以检验的行为：

- 记得消费者已经说过什么。
- 解释当前事实和处理依据。
- 给出符合风险等级的具体动作。
- 确保客服承诺得到后续执行。

## 18. 风险与应对

| 项目风险 | 影响 | 应对方式 |
| --- | --- | --- |
| 官方数据规模小且模板相似 | 指标虚高、泛化不足 | 按模板聚类切分，保留隐藏集，补充真实风格的合成压力测试 |
| 模型虚构金额或时间 | 造成错误承诺 | 业务事实只来自工具，生成后逐项校验 |
| 不良反应误诊 | 合规和安全风险 | 限制为流程分级，只描述可见信息，明确人工和专业医疗边界 |
| 风险提示过多 | 客服产生告警疲劳 | 证据化提示、分级队列、阈值校准和人工反馈 |
| 重复进线识别错误 | 错误关联其他消费者 | 使用平台消费者 ID，昵称只用于官方数据 Demo |
| 承诺时间理解错误 | 错误提醒或超时 | 模型提取语义，确定性日历计算，模糊时间要求人工确认 |
| Demo 依赖外网模型 | 现场不稳定 | 准备本地模型和固定数据，提供降级模式及一键启动脚本 |

## 19. 答辩材料建议

官方模板只有封面、内容页和结束页，可复制内容页形成 9 页主体结构：

1. 封面：知微客服副驾、赛道和队伍名称。
2. 真实问题与数据：客服为什么看不清、判不准、跟不住。
3. 产品全景：右侧插件、主管看板和服务闭环。
4. 日常接待副驾：全轨迹、事实核验、回复和动作。
5. 不良反应处置：风险分级、多模态资料和专项闭环。
6. 服务承诺跟踪：承诺抽取、时间计算和履约验证。
7. Agent 与技术架构：模型、工具、状态机和人工确认。
8. 评测与业务价值：真实指标、效率对比和 Token 成本。
9. 路线图与结束页：初赛能力、决赛增强和落地方式。

答辩应围绕一个消费者的完整故事展开，而不是逐项朗读功能。最能体现主题的表达是：系统不只帮助客服“说得更像人”，还帮助团队记住消费者经历过什么，并完成已经答应的事情。

## 20. MVP 完成标准

满足以下条件才可认为作品达到可参赛状态：

- 用户能在工作台中切换真实数据会话并看到对应订单与工单。
- 普通场景能够完成识别、查询、回复、人工确认和状态更新。
- 不良反应案例能够完成分级、信息收集、工单创建和回访跟踪。
- 承诺能够从最终客服消息中生成任务，并随业务状态进入提醒、超时或履约状态。
- 主管能从看板定位高风险和超时事项并执行处置。
- 关键模型结论都能回溯到消息、订单、工单或规则证据。
- 离线评测按会话和模板隔离，PPT 中只展示实际测得结果。
- Demo 在断网或模型不可用时有明确降级策略，不出现空白页面或无法继续的流程。
