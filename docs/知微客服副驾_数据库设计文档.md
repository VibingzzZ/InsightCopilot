# 知微客服副驾数据库设计文档

**版本**：v0.1（初赛 Demo 后端准备）  
**日期**：2026-09-13  
**状态**：开发契约草案

## 1. 设计目标与边界

本设计服务于当前一个月、三人团队的可运行 Demo，目标是让以下链路在数据库中可重复演示：

1. 选择消费者会话，读取消息、订单、历史工单和服务轨迹。
2. 对会话保存意图、情绪、风险、缺失信息和证据引用。
3. 以“预览 -> 人工确认”方式创建工单、催办、升级和回访任务。
4. 从客服最终发送消息生成服务承诺，计算截止时间并进入履约队列。
5. 通过 `demo/reset` 在现场恢复固定初始状态。

不在本阶段实现真实退款、真实打款、真实电商平台写操作或医疗诊断。模型结果允许使用 Mock，业务事实、状态流转、截止时间和审计由确定性服务负责。

## 2. 数据基线与技术决策

### 2.1 官方数据基线

导入文件：`赛题 1：数据共情者-业务数据.xlsx`。

| 来源 | 数据量 | 运行时用途 |
| --- | ---: | --- |
| 聊天记录 | 998 条消息 | 会话重建、证据引用、承诺抽取 |
| 订单 | 113 条 | 商品、金额、订单状态和物流事实 |
| 五类工单 | 80 条 | 售后、打款、物流、不良反应、退货 |
| 会话 | 138 个 | 客服队列与会话详情 |

五类工单来源分别为：补发换货、线下打款、物流、不良反应、售后退货。原始 Excel 只作为离线导入源，不直接被 API 或模型读取。

### 2.2 技术选型

- 首期使用 SQLite 文件数据库，便于单机演示和 `pytest` 测试。
- ORM 使用 SQLAlchemy 2.x，迁移使用 Alembic；字段类型和约束按 PostgreSQL 可迁移方式设计。
- 时间统一保存为带时区的 UTC；接口按 RFC3339 返回，前端可显示为 `Asia/Shanghai`。
- 金额统一保存为整数分（`*_cent`），禁止在业务计算中使用浮点数。
- 主键使用稳定字符串 ID，优先复用官方业务编号（如 `S00015`、订单号、工单号），内部生成的事件、承诺和动作使用 UUID。
- 所有业务写操作带 `request_id` 和 `idempotency_key`，支持重复请求安全重试。

## 3. 领域模型

```text
consumer 1 ─── N service_session 1 ─── N message
    │                  │ 1              │
    │                  ├── N sales_order ─── N service_event
    │                  ├── N service_ticket ─┘
    │                  ├── N promise
    │                  └── N ai_analysis
    └── N service_event

service_session 1 ─── N action_execution 1 ─── N audit_log
service_ticket 1 ─── N service_event
```

概念上的 `session`、`order`、`ticket` 表在物理库中分别命名为 `service_session`、`sales_order`、`service_ticket`，避免 PostgreSQL/SQLite 保留字和歧义。

## 4. 核心表设计

### 4.1 `consumer` 消费者

| 字段 | 类型 | 约束/说明 |
| --- | --- | --- |
| `consumer_id` | `TEXT` | PK；系统生成的稳定脱敏 ID |
| `display_name_masked` | `TEXT` | 必填；如 `魏h**`，只用于界面展示 |
| `nickname_hash` | `CHAR(64)` | 必填、唯一；用于跨会话归并，不可反推原值 |
| `risk_level` | `TEXT` | `L0/L1/L2/L3`，默认 `L0` |
| `risk_note` | `TEXT` | 脱敏后的运营备注，不放支付/地址原文 |
| `created_at` / `updated_at` | `TIMESTAMPTZ` | 必填 |

导入时用规范化昵称计算哈希；原始昵称不落运行库。昵称掩码仅保留首字符和有限尾部字符。

### 4.2 `service_session` 会话

| 字段 | 类型 | 约束/说明 |
| --- | --- | --- |
| `session_id` | `TEXT` | PK；官方会话 ID，如 `S00015` |
| `consumer_id` | `TEXT` | FK -> `consumer.consumer_id` |
| `store_name` | `TEXT` | 店铺名称 |
| `scene_major` / `scene_minor` | `TEXT` | 官方场景字段 |
| `status` | `TEXT` | `open/closed/pending` |
| `started_at` / `ended_at` | `TIMESTAMPTZ` | 会话起止时间 |
| `last_message_at` | `TIMESTAMPTZ` | 队列排序字段 |
| `intent_primary` / `intent_secondary` | `TEXT` | Agent 结构化结果，可空 |
| `emotion` | `TEXT` | `neutral/concerned/angry/urgent/unknown` |
| `risk_level` | `TEXT` | `L0/L1/L2/L3` |
| `summary` | `TEXT` | 当前任务相关摘要，不代替原始消息 |
| `unresolved_count` | `INTEGER` | 未解决事项数量，非负 |
| `source_import_batch` | `TEXT` | 导入批次号 |
| `created_at` / `updated_at` | `TIMESTAMPTZ` | 必填 |

索引：`(status, last_message_at DESC)`、`(risk_level, last_message_at DESC)`、`(consumer_id, last_message_at DESC)`。

### 4.3 `message` 消息

| 字段 | 类型 | 约束/说明 |
| --- | --- | --- |
| `message_id` | `TEXT` | PK；优先使用官方 `message_id` |
| `session_id` | `TEXT` | FK；必填 |
| `seq_no` | `INTEGER` | 必填；同一会话唯一且从 1 递增 |
| `sent_at` | `TIMESTAMPTZ` | 必填 |
| `role` | `TEXT` | `buyer/agent/system` |
| `sender_label` | `TEXT` | 已脱敏的发送方标签 |
| `content_type` | `TEXT` | `text/image/card/mixed` |
| `message_text` | `TEXT` | 脱敏后的文本；原文不进入模型上下文以外的运行数据 |
| `chat_content` | `TEXT` | 结构化卡片的非敏感摘要，可空 |
| `image_path` | `TEXT` | 仅保存受控相对路径，可空 |
| `is_target_buyer_message` | `BOOLEAN` | 官方标记 |
| `related_order_id` | `TEXT` | FK -> `sales_order.order_id`，可空 |
| `related_ticket_id` | `TEXT` | FK -> `service_ticket.ticket_id`，可空 |
| `source_sheet` / `source_row_no` | `TEXT` / `INTEGER` | 可追溯到 Excel |
| `created_at` | `TIMESTAMPTZ` | 必填 |

唯一约束：`UNIQUE(session_id, seq_no)`。索引：`(session_id, sent_at, seq_no)`、`(related_order_id)`、`(related_ticket_id)`。

### 4.4 `sales_order` 订单

| 字段 | 类型 | 约束/说明 |
| --- | --- | --- |
| `order_id` | `TEXT` | PK；建议等于官方订单号 |
| `order_no` | `TEXT` | UNIQUE；对外展示编号 |
| `session_id` / `consumer_id` | `TEXT` | FK；可空/必填 |
| `store_name` | `TEXT` | 店铺 |
| `sku` / `product_name` | `TEXT` | 商品事实 |
| `quantity` | `INTEGER` | 非负 |
| `unit_price_cent` / `paid_amount_cent` | `INTEGER` | 非负，单位分 |
| `order_status` | `TEXT` | `pending/paid/shipped/received/refunding/refunded/closed/unknown` |
| `ordered_at` / `paid_at` / `shipped_at` | `TIMESTAMPTZ` | 来源时间，可空 |
| `carrier` | `TEXT` | 快递公司，可空 |
| `tracking_no_masked` | `TEXT` | 物流号脱敏展示值；原值不返回 API |
| `shipping_province` / `shipping_city` | `TEXT` | 仅保留省市，不保存详细地址 |
| `gift_description` | `TEXT` | 赠品 |
| `buyer_note_redacted` | `TEXT` | 脱敏买家留言 |
| `source_import_batch` | `TEXT` | 导入批次 |
| `created_at` / `updated_at` | `TIMESTAMPTZ` | 必填 |

### 4.5 `service_ticket` 统一工单

| 字段 | 类型 | 约束/说明 |
| --- | --- | --- |
| `ticket_id` | `TEXT` | PK；建议等于官方工单号 |
| `ticket_no` | `TEXT` | UNIQUE |
| `ticket_type` | `TEXT` | `replenishment_exchange/offline_payment/logistics/adverse_reaction/return`；与 Excel 五类工单一一对应 |
| `session_id` / `consumer_id` / `order_id` | `TEXT` | FK；会话和消费者必填，订单可空 |
| `reason` | `TEXT` | 脱敏原因摘要 |
| `priority` | `TEXT` | `normal/urgent/critical` |
| `status` | `TEXT` | `draft/pending/in_progress/pending_customer/completed/cancelled` |
| `assignee` | `TEXT` | 处理人，可空 |
| `detail_json` | `JSON/TEXT` | 按工单类型校验的非敏感扩展字段 |
| `source_sheet` / `source_row_no` | `TEXT` / `INTEGER` | Excel 追溯 |
| `created_at` / `completed_at` | `TIMESTAMPTZ` | 必填/可空 |
| `updated_at` | `TIMESTAMPTZ` | 乐观锁更新时间 |

五类工单统一索引后，类型字段进入 `detail_json`，但必须使用 Pydantic 类型校验和字段白名单。首期扩展字段建议如下：

| 类型 | 允许的扩展字段（示例） |
| --- | --- |
| `replenishment_exchange` | `ship_sku`、`ship_product_name`、`quantity`、`warehouse`、`replacement_tracking_masked`、`expedite` |
| `offline_payment` | `payment_type`、`refund_reason_type`、`refund_amount_cent`、`related_tracking_masked`、`transfer_status`、`alipay_name_masked`、`alipay_account_masked` |
| `logistics` | `problem_type`、`carrier`、`package_tracking_masked`、`warehouse`、`solution`、`abnormal_flag` |
| `adverse_reaction` | `reaction_type`、`age_band`、`skin_type`、`product_name`、`batch_no_masked`、`affected_area`、`symptom_summary`、`onset_after`、`stopped_use`、`sought_medical_help`、`follow_up_status` |
| `return` | `package_type`、`return_reason`、`return_tracking_masked`、`refund_no_masked`、`receipt_advice`、`abnormal_flag` |

支付宝实名、支付宝账号、手机号、详细地址和其他支付凭据不允许出现在 `detail_json`。如后续确有受控线下流程需求，另建加密隔离库，由权限服务读取，主业务库只保存掩码和引用 ID。

### 4.6 `service_event` 服务时间线事件

| 字段 | 类型 | 约束/说明 |
| --- | --- | --- |
| `event_id` | `UUID/TEXT` | PK |
| `consumer_id` / `session_id` | `TEXT` | FK；至少会话必填 |
| `order_id` / `ticket_id` | `TEXT` | FK，可空 |
| `event_type` | `TEXT` | `message/order_status/ticket_status/promise/action/risk/follow_up` |
| `occurred_at` | `TIMESTAMPTZ` | 必填；按此字段排序 |
| `actor_type` / `actor_id` | `TEXT` | `buyer/agent/system/model/operator` 及对应 ID |
| `title` / `content` | `TEXT` | 脱敏展示文本 |
| `source_type` / `source_id` | `TEXT` | `chat/order/ticket/rule/action` + 原始 ID |
| `evidence_message_ids` | `JSON/TEXT` | 消息证据 ID 数组 |
| `metadata_json` | `JSON/TEXT` | 非敏感附加信息 |
| `created_at` | `TIMESTAMPTZ` | 必填 |

索引：`(consumer_id, occurred_at DESC)`、`(session_id, occurred_at)`、`(ticket_id, occurred_at)`。任何 Agent 结论都必须引用一个或多个 `source_id` 或 `evidence_message_ids`。

### 4.7 `promise` 服务承诺

| 字段 | 类型 | 约束/说明 |
| --- | --- | --- |
| `promise_id` | `UUID/TEXT` | PK |
| `consumer_id` / `session_id` | `TEXT` | FK；必填 |
| `source_message_id` | `TEXT` | FK -> `message.message_id`；只能是最终发送消息 |
| `promise_type` | `TEXT` | `refund/follow_up/replenishment/logistics/other` |
| `statement` | `TEXT` | 标准化承诺内容 |
| `owner_type` / `owner_id` | `TEXT` | `store/agent/team/system` |
| `due_at` | `TIMESTAMPTZ` | 必填；模糊时间在确认前可空 |
| `timezone` | `TEXT` | 默认 `Asia/Shanghai` |
| `status` | `TEXT` | `pending_confirmation/active/due_soon/overdue/fulfilled/changed/cancelled` |
| `verification_type` | `TEXT` | `ticket_completed/order_status/message_sent/manual` |
| `verification_ref` | `TEXT` | 关联工单/订单/消息 ID，可空 |
| `confirmed_by` / `confirmed_at` | `TEXT` / `TIMESTAMPTZ` | 人工确认信息 |
| `fulfilled_at` / `cancelled_at` | `TIMESTAMPTZ` | 状态时间 |
| `evidence_event_id` | `TEXT` | 履约证据事件，可空 |
| `version` | `INTEGER` | 乐观锁，默认 1 |
| `created_at` / `updated_at` | `TIMESTAMPTZ` | 必填 |

状态规则：`pending_confirmation -> active -> due_soon -> overdue -> fulfilled`；允许 `active -> changed/cancelled`、`due_soon -> changed/cancelled`，已履约不可回退。扫描任务只更新状态，不创造承诺。

### 4.8 Agent、动作与审计

#### `ai_analysis`

保存一次会话分析的结构化结果：`analysis_id`、`session_id`、`message_id`、`model_route`（`fast/reasoning/vision/mock`）、`intent_json`、`emotion`、`risk_level`、`missing_fields_json`、`evidence_message_ids`、`draft_text`、`provider_status`、`latency_ms`、`token_usage_json`、`created_at`。不得保存完整敏感模型上下文。

#### `action_execution`

保存预览和确认动作：`action_id`、`action_type`、`session_id`、`operator_id`、`idempotency_key`（唯一）、`preview_json`、`confirmed_payload_json`、`status`（`preview/confirmed/executed/failed/cancelled`）、`result_ticket_id`、`result_promise_id`、`request_id`、`created_at`、`confirmed_at`、`executed_at`。

#### `audit_log`

保存不可变审计记录：`audit_id`、`request_id`、`operator_id`、`action_id`、`entity_type`、`entity_id`、`operation`、`before_json`、`after_json`、`created_at`。敏感值只记字段名和掩码，不记原值。

## 5. 约束、索引与并发

- 所有外键启用 `ON DELETE RESTRICT`；演示重置通过事务恢复快照，不级联删除生产数据。
- `message(session_id, seq_no)`、`sales_order(order_no)`、`service_ticket(ticket_no)`、`action_execution(idempotency_key)` 必须唯一。
- 查询队列优先使用组合索引，详情页通过一次会话 ID 批量读取关联数据，避免 N+1 查询。
- `promise.version`、`service_ticket.updated_at` 用于乐观锁；版本不一致返回 `409 CONFLICT`。
- SQLite 启用 WAL、外键约束和 busy timeout；PostgreSQL 使用事务隔离 `READ COMMITTED` 即可满足 Demo。
- 所有状态变更与 `service_event`、`audit_log` 在同一事务提交，避免界面显示成功但时间线缺失。

## 6. 导入与脱敏流程

```text
Excel -> allowlist 字段读取 -> 规范化/类型校验 -> ID 关联
      -> 敏感字段掩码/丢弃 -> upsert 核心表 -> 生成 service_event
      -> 校验统计 -> 写入 import_batch
```

导入器要求：

1. 按会话、消息、订单、工单的依赖顺序导入；重复运行使用 `source_import_batch` 和业务主键幂等 upsert。
2. 从聊天记录、订单号、工单号建立关联；无法关联的记录保留 `unlinked_reason`，不得静默丢弃。
3. 只允许白名单字段进入运行库。支付宝账号、支付宝实名、手机号、详细地址等原值在内存中完成掩码后立即释放，不写日志。
4. 导入完成必须输出统计：消息 998、订单 113、工单 80、会话 138，并报告未关联数量、脱敏数量和失败行。
5. `import_batch`（可先作为管理表）记录文件哈希、导入时间、各表行数、失败行数和脚本版本，便于复现。

## 7. Demo 快照与重置

增加管理表 `demo_snapshot(snapshot_name, baseline_json, created_at)`，保存三个演示场景的固定入口（退款、不良反应、赠品补发）及初始状态。`POST /api/demo/reset` 在一个事务中：

1. 锁定 Demo 数据库写入。
2. 清理 `action_execution`、演示期间生成的承诺/事件/分析记录。
3. 恢复订单、工单、承诺和会话的 baseline 状态。
4. 写入一次 `demo_reset` 审计事件并提交。

目标耗时小于 3 秒；失败则整笔回滚。重置不删除原始 Excel，也不改变导入基线。

## 8. 验收清单

- [ ] 998 条消息、113 个订单、80 个工单、138 个会话可通过外键关联查询。
- [ ] 任意会话详情能返回消息、订单、工单、事件和未完成承诺。
- [ ] 五类工单的类型字段通过白名单校验，敏感原值不在数据库 API 输出中。
- [ ] 高影响动作预览不改状态，确认后同事务写业务表、事件和审计。
- [ ] 承诺只从最终发送消息生成，状态扫描可模拟 due/overdue/fulfilled。
- [ ] 重复 `idempotency_key` 不重复建单；并发更新冲突返回 409。
- [ ] SQLite 初始化、导入、重置命令可在 README 中一条命令复现，迁移脚本可切换 PostgreSQL。

## 9. 后续扩展

当真实后端接入后，再将高频 `detail_json` 字段迁移为五张一对一扩展表；增加知识库、风险事件、工作日日历和模型成本明细表。扩展不得改变本文件定义的核心 ID、事件证据和承诺状态契约。
